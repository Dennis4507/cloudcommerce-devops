# Git Workflow — Deep Dive

## What is Git?

Git is a version control system. It tracks every change made to every file in your project over time. Every change is recorded with who made it, when, and why. You can go back to any point in history, compare changes, and collaborate without overwriting each other's work.

GitHub is a platform that hosts Git repositories remotely — it is not Git itself. Git is the tool, GitHub is the storage location.

## The Three-Stage Workflow

Every change in Git goes through three stages:

```
1. Working Directory  → you make changes to files
        ↓  git add
2. Staging Area       → you select which changes to include
        ↓  git commit
3. Repository         → changes are permanently recorded
```

Think of it like packing a shipment:
- **Working Directory** = items on your desk
- **Staging Area** = items you've placed in the box (selected for this shipment)
- **Commit** = the sealed, labelled box sent permanently

The staging area exists so you can be selective. If you changed 10 files but only want to commit 3 of them, you stage only those 3.

## The Core Commands

```bash
git status              → show current state of working directory and staging area
git add <file>          → stage a specific file
git add .               → stage all changed files
git commit -m "message" → record staged changes permanently
git push                → send commits to GitHub
git log --oneline       → show commit history (newest first)
git pull                → fetch and merge latest changes from GitHub
```

Run `git status` constantly. Before staging, after staging, before committing. It costs nothing and prevents mistakes.

## Commit Messages — Conventional Commits

Commit messages follow a standard format used across professional teams:

```
type: short description of what and why

Types:
  initial  → first commit
  feat     → new feature or file added
  fix      → something broken was fixed
  docs     → documentation only changes
  refactor → code restructured without changing behaviour
  chore    → setup, config, housekeeping
```

Examples from this project:
```
initial: add .gitignore
docs: add project README with architecture and tech stack
feat: add terraform environment files and project screenshots
refactor: separate providers.tf, add tfvars, add vpc module
chore: add csv and credentials patterns to gitignore
```

Good commit messages tell a story. Looking at the log six months later, you understand exactly what happened and why.

## The .gitignore — Your Security Guard

The `.gitignore` file tells Git which files to never track, regardless of `git add`. This is your first line of defence against accidentally committing secrets.

What we block:
```
*.tfstate      → Terraform state files (contain resource IDs, sometimes secrets)
*.pem          → SSH private keys
*.key          → any private key
*.csv          → credential export files
.env           → environment variable files (often contain passwords)
*accessKeys*   → AWS credential files
.terraform/    → Terraform's local cache (can be 100MB+, regenerated by init)
```

What we allow:
```
*.tfvars            → our variable values (non-sensitive config)
*.pub               → SSH public keys (designed to be shared)
terraform.lock.hcl  → provider version lock (should be committed)
```

The rule: if it contains a secret, a password, a key, or can be regenerated — gitignore it.

## Branches — Parallel Timelines

Git supports branches — independent lines of development that don't interfere with each other.

```
main branch      → stable, working code
feature branch   → experimental changes in progress
```

Professional workflow:
```
git checkout -b feature/add-monitoring   → create new branch
(make changes)
git add . && git commit -m "feat: ..."
git push origin feature/add-monitoring
(open Pull Request on GitHub)
(code review)
git merge into main
```

For this solo portfolio project we work directly on `main` for simplicity. In a team environment, every change goes through a branch and a pull request.

## Why Git Push is Not Optional

Code that only exists on your local machine is lost if:
- Your laptop is stolen
- The hard drive fails
- Windows corrupts the filesystem

`git push` makes your work permanent on GitHub. We treat it the same as saving a document — do it after every meaningful checkpoint, not just at the end of the day.

The discipline we follow in this project:
```
Every checkpoint = git add + git status + git commit + git push + README update
```

## Reading git log

```bash
git log --oneline

783501c feat: add ec2, ecr, iam modules and ssh public key  ← most recent
f0f946b refactor: separate providers.tf, add tfvars, add vpc module
fb92725 feat: add terraform environment files and project screenshots
bd02605 chore: add csv and credentials patterns to gitignore
59aded3 docs: add project README with architecture and tech stack
77fd7f5 initial: add .gitignore                             ← first commit
```

The short hash (e.g. `783501c`) is a unique fingerprint for that commit. You can always return to any commit using its hash. The log reads newest to oldest.

## Interview Talking Points

- "I use conventional commits — every message starts with a type prefix so the history reads as a structured changelog"
- "The .gitignore is the first thing I set up in any project — it prevents secrets from ever reaching GitHub, which is especially critical with AWS credentials"
- "I commit frequently with meaningful messages rather than one large commit at the end — this makes it easy to identify when and why something changed if a bug is introduced"
- "Git staging lets me be intentional about what goes into each commit — I can change 10 files but commit only the 3 that are related, keeping the history clean"
